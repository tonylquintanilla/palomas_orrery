2. Findings, most important first

1. The neighbourhood rule conflicts with the promise that every item in a centre's branch can be drawn there. Atens can be listed under Venus while still orbiting the Sun, but their Sun-centred answers cannot be used directly in a Venus-centred scene. INFERRED -- Rules 1, 3 and 7; data/objects_config.json, canonical_center; gallery/assembler/resolver.py, resolve. The builder would need additional Venus-centred JPL answers or a rule excluding those items from that view. GitHub

2. The Sun view cannot yet mix a planet's satellites with its planets and spacecraft. The assembler rejects an object when its stored centre differs from the scene's centre, so it rejects the Earth-centred Moon in a Sun-centred scene. VERIFIED -- gallery/assembler/resolver.py, resolve, the FrameRejectionError check; interactive.html, SOLAR_SYSTEM_DRIVER. Rule 7 needs a change to scene assembly, not merely a new drawer. GitHub

3. Adding a parent's position to its child's position is mathematically sound, but it does not make either position more accurate. Both positions must refer to the same instant, use the same axis directions and units, and remain inside their own trustworthy periods. INFERRED -- Rule 5; gallery/assembler/render_orbits.py, propagate_marker; data/solar-system/coverage_index.json, each object's trust. The errors add rather than cancel, so the result can be visibly wrong when viewing a Moon closely, comparing a spacecraft with a moon or examining an encounter. This is not the forbidden subtraction of two large JPL answers. GitHub

4. The site's overall date limit is not a safe date limit for every moon. The November 7 cache gives the Moon a trust period of about 3.43 days on either side of its elements date, and Io only about 0.22 day, while the overall window excludes such locally centred objects. VERIFIED -- tools/gallery_cache_builder.py, TRUST_WINDOW_PARTICIPANT_FRAME; data/solar-system/coverage_index.json, objects.moon.trust and objects.io.trust; gallery/assembler/resolver.py, resolve. A mixed view must check each object's limit and explain any omission. GitHub +2

5. Today's Go To is not yet the close-up focus described in Rule 2. It changes the viewing frame around the scene's origin, and Solar System Go To fits the body's whole orbit rather than moving the view's origin to the body's position. VERIFIED -- interactive.html, ssGo, sunFocusOn and sunFrameOn. A comet or moon close-up away from the Sun needs a further camera operation, even though it must not become a new JPL centre. GitHub +1

6. A historical encounter cannot use the page's present-day date and ordinary position cache. The Psyche-Mars flyby occurred on May 15, 2026, but initSunExhibit always supplies today's date, and resolve refuses dates outside the current cache's overall window. VERIFIED -- interactive.html, initSunExhibit; gallery/assembler/resolver.py, resolve; data/objects_config.json, psyche_spacecraft.path.events. An encounter needs its own dated viewing context and an explicit return to today's context. GitHub +2

7. The existing spacecraft path cannot safely provide a close-up Mars flyby by itself. The nightly builder fetches the Psyche path using the spacecraft's configured Sun centre, including the flyby window, but this does not give a Mars-centred answer. INFERRED -- tools/gallery_cache_builder.py, fetch_path_by_plan; gallery/assembler/render_spacecraft.py, build_spacecraft_traces. Fetching the spacecraft directly around Mars during that encounter would preserve the no-subtraction rule and allow a meaningful close-up. GitHub

8. Pluto is an exception to the rule that every orbiting child is fetched around its named parent. Both Pluto and Charon are presently fetched around their shared centre of mass, called the barycentre, while Charon's listed parent is Pluto. VERIFIED -- data/objects_config.json, objects entries pluto and charon, canonical_center: "@9"; tools/gallery_cache_builder.py, process_object. A true Pluto-centred view would therefore require different fetches or a separately named barycentre view. GitHub +1

9. Lagrange points cannot be added as ordinary orbiting children. The Earth-Moon points numbered 3011-3015 have JPL positions relative to Earth, but an ordinary two-body orbit is not an appropriate drawing for them. VERIFIED -- documentation/SIZING_earth_moon_lagrange_20260907.md, proposed epoch-marker case; tools/gallery_cache_builder.py, process_object; gallery/assembler/assemble.py, assemble_scene. The builder, its checks and the assembler need a fourth served shape: a position at a stated time, without pretending it has an ordinary orbit. GitHub +1

10. The feature renderer already knows how to place a body's shells away from the scene's centre. It accepts a position for each body and uses that position when constructing rings, belts and shells, but the Solar System room currently omits those features altogether. VERIFIED -- gallery/feature_renderers.js, buildFeatureTraces; interactive.html, EXHIBITS["solar-system"].compose. The smaller change is to supply dependable positions and combine the existing feature drawings, rather than create a second shell-rendering system. GitHub +1

11. Changing the drawer without changing the page's room machinery would break existing behavior. The Solar System room has its own search, group folding, automatic spacecraft companions, Go To, Home and Reset, while the Sun and Earth rooms use different arrangements. VERIFIED -- interactive.html, EXHIBITS, solarSystemPositionFiles, ssBuildRows, ssWireRow, ssTickCompanions, ssHome, ssReset and sunReset; gallery/solar_system_drawer.js. The new shared drawer must retain those visitor actions, including their different starting states. GitHub +2

12. The nightly build does not yet serve the proposed tree or alternate centre-specific answers. It builds each object from one configured JPL centre, while the page reads the existing room rows directly from objects_config.json. VERIFIED -- tools/gallery_cache_builder.py, process_object, run_build and serve_drawings; interactive.html, solarSystemPositionFiles; data/objects_config.json, rooms.solar-system.drawer.rows. Tree definitions can begin as additional configuration, but new physical centre views require new cache records, checks and a way to identify the centre of each answer. GitHub +3

13. Not every new centre requires new JPL fetching. Earth-Moon, Jupiter-Io and Saturn-Titan already have the appropriate parent-centred orbital answers, while Mars needs Phobos and Deimos, Pluto needs special handling, and neighbourhood objects displayed from another centre need separate answers. INFERRED -- data/objects_config.json, canonical_center; data/solar-system/coverage_index.json, stored_center; tools/gallery_cache_builder.py, process_object. The root's moon combinations need new assembly logic more than new fetching, provided the separate trust limits are enforced. GitHub +2

14. The Mars build must still complete the four rulings in L-514 rather than merely add a centre name. Phobos and Deimos exist in the orrery but lack export keys, and neither appears in the website's objects configuration. VERIFIED -- Orrery celestial_objects.py, Phobos and Deimos entries; gallery data/objects_config.json, objects; LEDGER_CONSOLIDATED.md, L-514. Their JPL periods, sourced descriptions and accuracies, initial unticked state, full text boxes and Mars's fixed centre row remain build work; the Earth drawer also needs the fixed Earth row Tony identified. 15. The Earth room contains drawings that cannot be shared simply by moving its shells. Its Sun direction, day-night boundary, Moon's trusted arc and pole of date are assembled specially, rather than being ordinary entries in the feature renderer. VERIFIED -- gallery/earth_geometry.js, composeScene and moonBox; interactive.html, EARTH_DRIVER and EXHIBITS.earth.compose; gallery/feature_renderers.js, buildFeatureTraces. Those drawings need their existing calculations and their own dates preserved when the Earth branch becomes reusable. GitHub +1

16. A moon's orbit moved to its parent's current position is not its complete path around the Sun. The present orbit drawing is a fixed ellipse, while the parent moves during the moon's successive revolutions. INFERRED -- gallery/assembler/render_orbits.py, sweep_conic and build_orbit_traces; Rule 5. Translating that ellipse is suitable for showing the local orbit beside the planet at one moment, but it must not be described as the moon's actual Sun-centred trajectory over time. GitHub

17. The main asteroid belt's cloud needs to survive as a drawing even though it is not an orbiting body. Its drawing is named by a Solar System room row, and the builder already has a special step to copy such room-owned drawings. VERIFIED -- data/objects_config.json, rooms.solar-system.drawer.rows; tools/gallery_cache_builder.py, serve_drawings; gallery/feature_renderers.js, buildRoomCloud. Moving that row into a tree without preserving its drawing reference would remove an existing exhibit. GitHub +1

18. The tree needs separate meanings for physical parent and visitor placement. The current parent records such relationships as Moon under Earth and Charon under Pluto, while the proposed Atens under Venus and missions under Earth are arrangements for navigation. INFERRED -- data/objects_config.json, objects[].parent and rooms.solar-system.drawer.rows; Rule 1. Replacing the physical parent with the visitor's chosen grouping would make the record misleading; a separate navigation relationship is the smaller change. GitHub +1

19. A strictly single-parent tree cannot express every required cross-listing by itself. Lagrange points must appear under both members of their pair, and encounters must appear under both the encountered body and the spacecraft. INFERRED -- Rules 4 and 6; data/objects_config.json, proposed tree keys. The simplest method is one underlying record with references to it from other branches, so ticking or opening either listing reaches the same object.

Both have the Sun as their physical centre, but the root allows everything to mix while the Sun branch lists only its own descendants. QUESTION -- WHAT Tony wants the visitor to see; interactive.html, EXHIBITS.sun, EXHIBITS["solar-system"]; Rule 3. The two views can share one JPL centre without being the same place in the navigation tree. GitHub

21. The tree needs a settled rule for groups lying between two parents. The current drawer deliberately places asteroid and spacecraft groups between selected planetary rows, but their location in Tony's nested branches is a visitor-facing choice. QUESTION -- WHAT Tony wants; data/objects_config.json, rooms.solar-system.drawer.rows, including aten, spacecraft and main_belt groups. 22. Addresses, missing centres and encounter exits need rules before the page is replaced. The present page recognizes ?exhibit=solar-system, ?exhibit=sun and ?exhibit=earth, but it has no general centre-and-date address. 23. Look Toward can use existing direction information, but the March equinox example needs its own date. The Earth room already derives the direction to the Sun from Earth's served orbital elements, yet the current page has no way to open an arbitrary historical date for that viewing act. INFERRED -- interactive.html, EARTH_DRIVER, initSunExhibit and navigation camera functions; orrery visualization_utils.py, add_look_at_object_buttons; Rule 8. Look Toward at today's date can be implemented separately from a March equinox demonstration, without introducing general date selection. GitHub +1

24. The simplest overall change is to keep one copy of each existing object and attach navigation references to it. This preserves the present elements, features, source information and object identities while allowing several branches to reveal the same thing. INFERRED -- data/objects_config.json, objects, features and rooms; gallery/assembler/resolver.py, resolve. It avoids duplicating physical records into separate room definitions and fits the stated goal without redesigning the orrery's object catalogue. GitHub +1

3. View of the build order

The proposed order is sound if step 2 is treated as a compatibility build, not merely a drawer replacement. Step 1 should add and check navigation information without changing the existing object records or nightly output. Step 2 should introduce shared scene assembly, safe placement of parent-centred objects, per-object trust checks and shared drawer behavior, while keeping all three existing addresses, arrivals, text boxes, Home, Reset, search and spacecraft paths working; the existing EXHIBITS views can remain as temporary adapters. Step 3 should add Mars, Phobos and Deimos from JPL and complete L-514, using Earth as the working comparison. Step 4 should add dated, encounter-centred spacecraft fetching and navigation, then the historical missions. I would put a tested Sun/Earth compatibility checkpoint between steps 2 and 3, and a nightly-cache validation checkpoint before enabling each new centre.
